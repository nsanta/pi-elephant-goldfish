Goal — give every future plan a friendly, visual review surface

Adopt the artifact system described in update.md: a single-file HTML design system (artifacts/_template.html) plus agent rules, so that plans, dashboards, and reviews are generated as self-contained HTML artifacts you can open and review in the browser — like this one. Markdown stays the source of truth; HTML is the human-facing projection.

  • Plans become reviewable dashboards (charts, diagrams, decision tables) instead of walls of prose.
  • One design system: five palettes, light/dark, Chart.js + Mermaid theming that stays consistent across artifacts.
  • Fits this repo's artifact-first culture: files over chat, human gates before implementation.

Markdown vs HTML — What Lives Where

ContentHomeWhy
Agent rules AGENTS.md (markdown) Agents parse markdown; it must diff cleanly and load as context
Plan of record (tasks, AC) Markdown Greppable, diffable, survives review loops
EGM briefs / drafts / reports Markdown Already artifact-first in this repo; Goldfish reviewers read markdown
Design system / template HTML (_template.html) It is the visual system — markdown cannot express it
Plan review artifacts, dashboards HTML (generated) Charts, diagrams, toggles — friendlier human review

Single-writer rule: markdown feeds HTML, never the reverse.

D2 · Phases

D3 · Delivery shape

Subagent vs inline rules vs hybrid?

Recommended: hybrid — a user-global artifact-forge subagent keeps generation context-isolated and reusable from any project; a thin AGENTS.md rule stays for triggering and small edits. Packages can't ship agents, so cross-machine sharing is a P4 package.

D4 · Git policy

Version generated artifacts or gitignore them?

Recommended: version (review records). Switch to gitignore if artifacts start accumulating noise.

D5 · Defaults

Palette + mode defaults

Recommended: dusk + light (spec defaults), per-artifact override via prompt.
