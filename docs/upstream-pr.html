Draft material: contributing the Pi port upstream

Status: internal draft only. Nothing here has been submitted. This document collects the analysis and ready-to-paste material for a possible future contribution of this port's existence back to google/elephant-goldfish-model. Every submission action is gated on the owner's decision.

Context

Upstream harness policy (from their docs/harnesses.md):

EGM is one set of skills and personas. This repository serves as the plugin source for each supported harness. No harness gets a fork of the skill text.

Harness differences live in per-harness manifests and delegation documentation, never in divergent copies of skills/ or agents/.

What this port did, relative to that policy:

  • Standalone package. The vendored content (skills/, agents/, resources/) stays byte-identical to upstream except for minimal scripted substitutions (scripts/adapt-pi.mjs, see UPSTREAM.md), so upstream keeps a single authoritative content set and this repo remains a consumer, not a fork.
  • Scripted adaptations. Every pi-specific textual difference is generated by the adaptation script, and the suite proves regeneration fidelity over a pristine upstream tree (tests/unit/adaptation.test.ts).
  • Sync idempotence proof. scripts/sync-upstream.sh copies content, re-applies the scripted adaptations, and fails on unexpected upstream drift; phase 1 verification (see TESTING.md) recorded deterministic regeneration from pristine upstream with checker negative controls.

Option A — upstream pi manifest + harness row + per-harness delegation handling

Upstream adds Pi as a first-class supported harness:

  • Manifest: a package.json with a pi key ("pi": { "extensions": [...], "skills": [...], "prompts": [] }) alongside the existing plugin.json / .claude-plugin/ / .codex-plugin/ catalogs.
  • Harness row: Pi in the docs/harnesses.md install and delegation tables.
  • Per-harness delegation handling: the skills' "spawn a subagent" phrasing would need the same parameterized delegation treatment the other harnesses get, and upstream would carry an adapter — an extension providing egm_ask/egm_goldfish equivalents (interactive gates and zero-context reviewer spawning) — inside the Google repository.

Trade-offs:

  • (+) Matches the upstream policy exactly: one content set, harness differences in manifest + delegation docs; pi users get a first-party install path.
  • (+) The extension is small and depends only on pi's public extension API (tools, commands, --print subprocesses).
  • (−) Upstream inherits a TypeScript extension that must track the pi host API across pi releases — a new maintenance surface and CI matrix cell they do not have today.
  • (−) The skills would need another delegation variant; upstream has so far kept harness-specific mechanics out of the skill bodies.
  • (−) End-to-end verification for pi (their bar, below) would run in upstream CI or stay manual-only, like the Codex/ChatGPT integrations.

Option B — upstream links to this external pi package from docs/harnesses.md

Upstream treats Pi the way omp was treated: a "Community" install row plus a support-status section pointing at this external package (omp precedent: issue #186).

Trade-offs:

  • (+) Zero new maintenance burden upstream; no code or skills changes; a docs-only PR.
  • (+) Accurate support status: this repo records its own verification evidence and pins the upstream revision it tracks.
  • (−) Not first-party: pi users depend on this external repo staying in sync with upstream.
  • (−) pi install git:... resolves to the external repository, not google/elephant-goldfish-model.

Recommendation: Option B. The port exists and is verified as an external package; a docs-only row matches the omp precedent and imposes no runtime maintenance on upstream. Option A can follow later if upstream wants a first-class pi harness.

docs/harnesses.md — Support-status section

**Pi** has a community package,
[pi-elephant-goldfish](https://github.com/nsanta/pi-elephant-goldfish), which vendors this
repository's content at a pinned revision and adds a pi extension (`egm_ask`, `egm_goldfish`,
`egm_bootstrap`, `egm_state`, and `/egm-*` commands). Install with
`pi install git:github.com/nsanta/pi-elephant-goldfish` (Pi >= 1.4.0). Skills are invoked as
`/egm-<command>` (the extension registers one command per skill, so the same commands work in
TUI, RPC, JSON, and print modes). Verification evidence — including an end-to-end headless
review and a bootstrap run — is recorded in that repository's
[TESTING.md](https://github.com/nsanta/pi-elephant-goldfish/blob/main/TESTING.md). End-to-end
workflow fixtures are not yet automated for Pi.

Verification evidence they would require

Upstream's bar for a harness row has been a working install path with an end-to-end brainstorm → draft → review through plugin install. This repo's evidence:

  • Phase-by-phase harness verification record: TESTING.md — including a headless, uninterrupted /egm-review over a fixture (all five stages through 9 zero-context reviewer children, consolidated verdict catching every planted flaw) and a full egm_bootstrap run.
  • The remaining gap relative to their bar: the recorded evidence uses the dev install (pi -e .); the pi install git:... path is deferred to this repo's release checklist, and the interactive multi-turn flows (TUI gates mid-flow) are verified manually against the per-skill checklists in skills/*/TEST.md, not automated.
